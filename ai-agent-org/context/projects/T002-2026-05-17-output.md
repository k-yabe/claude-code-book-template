## エージェント定義の「あるべき基準」— レビュー用チェックリスト

### ■ 必須フィールド定義

```
各エージェント定義ファイルに含まれるべき項目：

[ ] agent_id         : 一意のエージェントID（命名規則に従っているか）
[ ] role             : 役割名（日本語 or 英語、統一されているか）
[ ] team             : 所属チーム（engineering / content / qa 等）
[ ] responsibilities : 責任範囲の列挙（具体的か、曖昧でないか）
[ ] input            : 受け取るインプットの形式・ソース
[ ] output           : 出力する成果物の形式・宛先
[ ] escalation_path  : ブロック時・判断不能時のエスカレーション先
[ ] do_not           : やらないこと（境界の明確化）
[ ] tools / files    : 参照するコンテキストファイル・使用ツール
```

### ■ 整合性チェック観点

```
philosophy.md との照合：
[ ] 「人間確認が必要なこと」に該当する行動を自律実行していないか
[ ] タスクステータス更新の責任が明確か（new-assigned→in-progress→done）
[ ] 引き継ぎ書（ai-handoffs/）への記録が責務に含まれているか
[ ] 「静かに壊れる」防止のためのエラー可視化が定義されているか

チーム間整合性：
[ ] 責任の重複がないか（2エージェントが同じ作業を担当していないか）
[ ] 責任の空白がないか（誰も担当しない領域が発生していないか）
[ ] オーケストレーター役が各チームに存在するか
```

### ■ 命名規則チェック

```
[ ] ファイル名：kebab-case（例：qa-engineer.md, tech-lead.md）
[ ] agent_id：snake_case または kebab-case で統一
[ ] role名：一貫した表記（Senior / Lead / Specialist など職位の統一）
```

### ■ 実行可能性チェック

```
[ ] responsibilitiesが「〜を担当する」レベルで具体的か
    （NG例：「品質を保証する」→ OK例：「成果物を philosophy.md のチェックリストに沿ってレビューし、ai-handoffs/ に記録する」）
[ ] inputが「どのファイル・タスクIDから受け取るか」まで明記されているか
[ ] outputの「書き出し先」が明記されているか
[ ] ブロック条件が具体的に定義されているか
```
